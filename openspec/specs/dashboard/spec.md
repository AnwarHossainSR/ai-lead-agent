## Requirements
### Requirement: The interface reflects the signed-in account and its role

The interface SHALL require sign-in before any workspace view, SHALL show who is signed in, SHALL provide sign-out, and SHALL not present controls for actions the signed-in role may not take.

#### Scenario: An unauthenticated visitor is sent to sign in

- **WHEN** a workspace view is opened without a session
- **THEN** the sign-in page is shown and no workspace data is rendered

#### Scenario: The signed-in account is visible

- **WHEN** a workspace view is open
- **THEN** the signed-in account and a sign-out control are shown

#### Scenario: A viewer sees no approval control

- **WHEN** a viewer opens the outreach review queue
- **THEN** the approve, reject and record-send controls are not presented

#### Scenario: A hidden control is also refused by the API

- **WHEN** a viewer issues an approval request directly
- **THEN** the API refuses it

### Requirement: Approvals are shown with who made them

The interface SHALL display the account that approved or rejected each outreach message, and the account that set a do-not-contact marker, alongside the time.

#### Scenario: An approved message shows its approver

- **WHEN** an approved message is displayed
- **THEN** the account that approved it and the time are shown

#### Scenario: A do-not-contact marker shows who set it

- **WHEN** a marked company or contact is displayed
- **THEN** the account that set the marker and the reason are shown

### Requirement: Observed, inferred and unknown are visibly distinct

The interface SHALL render a value the platform observed, a value it inferred, and a value it does not hold as three visually distinct states, and SHALL NOT present an inferred value with the same treatment as an observed one. An unknown value SHALL render as unknown and SHALL NOT render as an empty field, a dash, or a zero.

#### Scenario: An inferred value is marked

- **WHEN** an inferred value is displayed
- **THEN** it carries a marking distinguishing it from an observed value

#### Scenario: An unknown value says so

- **WHEN** the platform holds no value for a displayed field
- **THEN** the field renders as unknown rather than blank or zero

#### Scenario: An unmeasured score is not shown as zero

- **WHEN** a quality score was never measured
- **THEN** it renders as not measured rather than as a score of zero

#### Scenario: Generated content is labelled

- **WHEN** a research summary or a generated draft is displayed
- **THEN** it is labelled as generated by a model

### Requirement: Every claim links to its source

The interface SHALL display, for every claim carrying a source URL, a link to that URL, and SHALL display the time the claim was recorded. A claim whose evidence is a matched text or a cited fact SHALL make that evidence visible without leaving the page.

#### Scenario: A company links to where it was discovered

- **WHEN** a company is displayed
- **THEN** its discovery source URL is a link

#### Scenario: A technology detection shows what matched

- **WHEN** a technology detection is displayed
- **THEN** the text that matched and where it matched are visible

#### Scenario: An opportunity shows the evidence it cites

- **WHEN** an opportunity is displayed
- **THEN** the observations and detections it cites are visible

#### Scenario: A contact links to where it was published

- **WHEN** a contact with an email is displayed
- **THEN** the source URL for that detail is a link

### Requirement: The review queue shows a message with the facts it rests on

The interface SHALL present drafts awaiting approval one at a time, showing the full message text alongside the facts it cites, and SHALL require the message to be displayed before it can be approved.

#### Scenario: A draft is shown with its citations

- **WHEN** a draft awaiting approval is opened
- **THEN** the full message and the facts it cites are displayed together

#### Scenario: Approval acts on the displayed message

- **WHEN** a draft is approved
- **THEN** the approval applies to the message text that was displayed

#### Scenario: There is no bulk approval

- **WHEN** the review queue is inspected
- **THEN** it offers no action approving more than one message

#### Scenario: Rejection requires a reason

- **WHEN** a draft is rejected without a reason
- **THEN** the interface refuses and asks for one

### Requirement: An edit after approval is shown as revoking it

The interface SHALL show, when an approved message is edited, that its approval has been revoked and that it requires approval again.

#### Scenario: Editing an approved message shows the revocation

- **WHEN** an approved message is edited
- **THEN** the interface shows that the approval was revoked and the message is a draft again

#### Scenario: The revoked message cannot be treated as approved

- **WHEN** a message whose approval was revoked is displayed
- **THEN** it appears among drafts awaiting approval

### Requirement: Nothing in the interface sends a message

The web application SHALL contain no control, action or request capable of transmitting an outreach message.

#### Scenario: No send control exists

- **WHEN** the outreach views are inspected
- **THEN** they contain no action that transmits a message

#### Scenario: Recording a send is described as recording

- **WHEN** the control for recording a manual send is displayed
- **THEN** it states that it records an action already taken and does not send

### Requirement: Failed and incomplete pipeline states are visible

The interface SHALL display companies and leads whose pipeline stages failed, were blocked, were skipped, or fell below a threshold, as those states rather than as absent data.

#### Scenario: A blocked analysis is shown as blocked

- **WHEN** a company whose website analysis was blocked is displayed
- **THEN** the interface shows it as blocked rather than as never analysed

#### Scenario: An unreachable company is distinguishable from an unverified one

- **WHEN** an unreachable company and an unverified company are displayed
- **THEN** the two states are distinguishable

#### Scenario: A below-threshold company says why

- **WHEN** a company that had too little evidence for opportunity analysis is displayed
- **THEN** the interface states that reason

### Requirement: Analytics report counts and mark small samples

The interface SHALL display every rate together with the counts it was computed from, SHALL mark a rate below the configured reporting minimum, and SHALL NOT display a trend or comparison for a segment below that minimum.

#### Scenario: A rate shows its counts

- **WHEN** a response rate is displayed
- **THEN** the number of messages sent and responses received are displayed with it

#### Scenario: A small sample is marked

- **WHEN** a rate is computed from fewer than the configured minimum
- **THEN** it is displayed marked as below the reporting minimum

#### Scenario: No trend is drawn from a small sample

- **WHEN** a segment is below the reporting minimum
- **THEN** no trend line or comparison is displayed for it

### Requirement: The interface degrades rather than failing

The interface SHALL render a usable page when the API is unreachable, slow, or returns an error, displaying the condition rather than an unhandled error page, and SHALL bound every server-side request by a timeout.

#### Scenario: An unreachable API degrades the page

- **WHEN** the API is unreachable
- **THEN** the page renders with the condition displayed and no unhandled error page

#### Scenario: A slow API does not hang the page

- **WHEN** the API does not respond within the configured timeout
- **THEN** the page renders with the condition displayed

#### Scenario: A partial failure degrades only its panel

- **WHEN** one panel's data cannot be loaded
- **THEN** the remaining panels render normally and that panel shows the condition

### Requirement: The interface is navigable and readable

The interface SHALL be operable by keyboard, SHALL meet the project's configured contrast standard, and SHALL give every interactive control an accessible name. Automated accessibility checks SHALL run against the main views.

#### Scenario: The review queue is operable by keyboard

- **WHEN** the review queue is used without a pointing device
- **THEN** every action including approve, edit and reject is reachable and operable

#### Scenario: Automated checks pass on the main views

- **WHEN** the automated accessibility check runs against the lead list, lead detail and review queue
- **THEN** it reports no violation at the configured level

#### Scenario: Controls have accessible names

- **WHEN** the interface is inspected
- **THEN** every interactive control has an accessible name
