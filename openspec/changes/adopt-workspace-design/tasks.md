## 5. Dependency health sampling

- [x] 5.1 Add `dependency_health_samples` to `packages/database/src/schema/` — dependency, status, latency, sampled-at (design D6) — with a `failure_reason` alongside, and two CHECK constraints tying the columns to the status: a dependency that answered has a latency, one that did not has none; a status other than `up` says why. The status enum has deliberately no `unknown` value — a probe that did not run writes no row, and an absent row is what "unsampled" means, so storing `unknown` would make a gap indistinguishable from a probe that learned nothing
- [x] 5.2 Generate and apply the migration — `drizzle/0015_zippy_ma_gnuci.sql`, applied to the local database
- [x] 5.3 Add write and read helpers, the read returning the earliest sample it holds alongside the window — the read generates the bucket series and **left joins** the samples onto it, precisely so an unsampled bucket survives into the response as `status: null`. The natural implementation — grouping the samples that exist — silently drops every unsampled period and leaves the bar looking continuous. Several samples in one bucket resolve worst-wins, because a bucket that was down for part of it was not up
- [x] 5.4 Add the repeatable probe writing one sample per dependency per minute, reusing the existing health checks rather than duplicating them — the same `SELECT 1` and `PING` through the same timeout helper the health indicators use, rather than a second definition of "up" that could disagree with `/health`. A plain `unref`'d interval rather than a scheduled job: `add-background-jobs` owns scheduling and is unimplemented, and a one-minute probe justifies neither blocking on it nor a new dependency. A tick arriving while the previous one runs is skipped. A sample that cannot be written is logged and skipped — that minute renders as unsampled, which is true
- [x] 5.5 Add `GET /api/health/history` returning samples with unrecorded periods marked, never interpolated (spec: a gap in sampling is visible) — its own controller rather than a route on the health controller, and deliberately **not** `@Public()`: the three liveness endpoints exist for a load balancer, while a record of when each dependency was down is operational detail and sits behind the same sign-in as every other aggregate read
- [x] 5.6 Confirm by hand: a window reaching before the first sample reports the earlier part as unrecorded, and a sampling gap is left as a gap — both confirmed with samples at t−10, t−8 and t−2 minutes over a 14-minute window: the two buckets before the first sample and the two in the middle gap all came back `status: null`, never interpolated from either side. Both CHECK constraints refused their violations. Confirmed again live: `GET /api/health/history` shows `postgres` and `redis` sampled every minute since boot, with every bucket before boot unrecorded
