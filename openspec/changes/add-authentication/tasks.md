## 7. Audit log

- [x] 7.1 Append audit entries for sign-in, failed sign-in, sign-out, revocation, account creation, role change, disablement, and each consequential action — `apps/api/src/audit/`: `AuditService` (thin wrapper over `insertAuditEntry`, swallows and logs its own failures so an audit outage never fails the request it describes) plus `AuditEventInterceptor`, registered globally via `APP_INTERCEPTOR`. The interceptor audits every route carrying `@RequiresRole` — the same set task 5.2 already established as consequential — deriving the event name from the guard's own `action` string (`slugify.ts`) so there is one place that names an action, not two that could drift. `AuthService` audits sign-in/failed-sign-in/sign-out directly (these routes are `@Public()`, so they carry no `@RequiresRole` for the interceptor to key off). Account creation, role change and disablement (task 6.2) are covered for free since `AccountsController`'s routes already carry `@RequiresRole`. **Design decision**: there is no standalone "revoke a session" endpoint in this API — every session revocation happens either through sign-out (self) or account disablement (operator-initiated, which already revokes every session for that account as one step); the spec's "revocation" item is satisfied by those two audited events rather than a third, since a third would have no distinct action to describe
- [x] 7.2 Add a test asserting the audit writer's payload carries no password, hash, session id or model prompt — `audit/audit.test.ts`; structural rather than per-field-scrubbing: the interceptor and `AuthService`'s direct calls never put a request or response body into `detail` (only `event`, `outcome`, `accountId`, `subjectType`/`subjectId`, `sourceAddress`), so there is no code path for any of the four to reach the log. Exercised against real routes that handle all four: a real password at sign-in (failed and succeeded), a real password hash at account creation, a real session at sign-out, and a model-triggering route (`draftOutreach`)
